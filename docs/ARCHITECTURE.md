# 架构与工程取舍

## 目标与输入输出

输入是公开招聘正文、来源授权证据、结构化岗位观测，以及用户明确确认的画像和策略。输出是去重岗位台账、资格分流、证据索引、变更历史、Excel 和运行日报。每次运行用独立 `run_id` 关联这些记录。

Codex 承担非结构化信息发现和解释；确定性的 Python 校验负责把不完整输入留在待核实或隔离路径。核心运行只依赖 Python 标准库。

## 模块职责

| 模块 | 职责 |
| --- | --- |
| `SKILL.md` | 发现、采集、核验、恢复与汇报的执行协议 |
| `scripts/scout.py` | 数据契约、证据与来源校验、资格判断、事务入库、队列与报告 |
| `scripts/xlsx_writer.py` | OOXML 输出、公式文本防护、人工跟进回收、导出备份与替换 |
| `scripts/run_daily.py` | 能力预检、默认 dry-run、单实例锁、子进程超时和配置漂移检测 |
| `scripts/register_daily.ps1` | Windows 任务预览和显式注册 |
| `tests/fixtures.py` | 测试与演示共用的虚构证据工厂，不参与生产检索 |

## 为什么使用 SQLite 作为台账

Excel 适合浏览和人工输入，但不适合承担唯一键、历史观测和事务一致性。项目用 SQLite 管理 `jobs`、`observations`、`events`、`sources`、`evidence`、`leads`、`coverage`、`annotations` 与 `runs`，每次导出重建视图。

岗位键优先由企业、招聘批次和职位编号组成；没有编号才回退到保留关键参数的 URL。完全相同的观测重复写入会跳过，已有岗位正文复核不会被算作新增；旧观测也不能覆盖较新观测。

## 为什么将资格与匹配分开

资格判断回答“已知公开硬条件是否满足”，匹配分回答“当前规则下优先看什么”。未知事实进入待确认；明确不符进入历史与排除。匹配分是可解释的规则分数，不是模型概率，也没有资格豁免权。

岗位评估分为 `eligible`、`qualification_pending`、`verification_pending`、`history`。无法取得职位正文的入口独立保存在 `leads`，避免把搜索结果数当作可投岗位数。

## 证据完整性和来源真实性

登记证据时保留文本、URL、采集时间、工具引用、完整性标记和哈希；字段引用必须能在对应证据中找到。来源注册还限定官方页面或 ATS 的授权前缀。完整性校验能识别文件变动，但不能独立证明采集者诚实或网站内容正确；真实运行仍需要保存工具日志并抽样复核。

## 导出与失败处理

导出前读取“人工跟进”B:D 列并写回 `annotations`，然后备份旧工作簿、生成临时文件、检查期间是否发生编辑并替换最新文件。来自网页的公式样文本按字符串处理。工作簿缺少预期结构、被占用或导出冲突时保留错误状态和可检查文件。

运行锁拒绝并发写入；超时尝试清理自身启动的进程树，清理不能确认时保留锁。画像与策略变化会阻断运行，不能由网页内容直接修改。完成比例的分母是当前计划的 24 项发现任务，不是互联网岗位总数。

## 当前取舍与下一步验证

标准库 OOXML 减少安装依赖，代价是维护格式和兼容性验证。单机 SQLite 简化部署，当前不支持多人同时编辑。检索预算目前主要由执行协议约束，尚未实现工具调用硬限额网关。真正上线还需验证动态网站、长期运行、来源误判率、任务失败率及运行成本；没有相应实测前不把它们写成性能成果。
